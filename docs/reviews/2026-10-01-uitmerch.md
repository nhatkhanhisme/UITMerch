**UITMerch function, logic, and security review — 1 October 2026**

Reviewed commit: `c08cbf1`. Scope: backend controllers/services/entities, authentication, order and inventory flows, notifications, catalog/events, AI search, frontend API/state/checkout, configuration, migrations, and existing test structure. This is a local code review with frontend build and dependency checks. Backend behaviors described below were not reproduced through a running server because the installed Java runtime could not start. Live deployments, database grants, and Supabase bucket policies were not inspected.

The app has a substantial feature base. The highest priorities are durable OTP lockout, session revocation, order/inventory concurrency, and linking logged-in purchases to the customer account. No application source was changed during this review.

**High-priority findings**

**F01 — High: failed OTP attempts are rolled back, defeating the lockout.**

Evidence: [AuthService.java](../../backend/src/main/java/com/uitmerch/backend/auth/service/AuthService.java), `verifyEmail` at line 69 and failure handling at line 91; `resetPassword` at line 275 and failure handling at line 294. Both transactional methods save the attempt count/lock timestamp and immediately throw `InvalidOtpException`, which extends the runtime `AppException`. Spring's default runtime-exception rollback undoes those writes. The verification and reset submission endpoints also lack controller-level rate limiting. This makes online guessing substantially easier than the intended five-attempt limit.

Fix: commit failed-attempt accounting before returning the error, using a carefully scoped transaction boundary, and apply limits per account and client. Make attempt increments atomic under concurrent requests. Bind each OTP to its purpose. Do not broadly disable rollback for all authentication errors. This conclusion follows the documented [Spring rollback behavior](https://docs.spring.io/spring-framework/reference/data-access/transaction/declarative/rolling-back.html).

Verification: call the Spring-managed service with five wrong codes, using separate requests/transactions; reload the OTP from the database after each error. The count must persist, and the correct code must be rejected while locked. The existing Mockito tests assert changes to a mocked entity, which cannot verify transaction commits.

**F02 — High: deactivation, role changes, and password reset do not revoke existing sessions.**

Evidence: [JwtAuthenticationFilter.java](../../backend/src/main/java/com/uitmerch/backend/common/config/JwtAuthenticationFilter.java), line 54; [AuthService.java](../../backend/src/main/java/com/uitmerch/backend/auth/service/AuthService.java), `refreshToken` at line 144 and password update at line 308; [AdminService.java](../../backend/src/main/java/com/uitmerch/backend/admin/service/AdminService.java), lines 54 and 62. Login checks `isActive`, but refresh does not. The request filter trusts the JWT's role without checking current account state. Admin updates only the user row; password reset only changes the password hash. Access tokens default to 24 hours, and refresh tokens default to seven days.

Impact: a deactivated account can mint new tokens; a demoted admin can continue using the old admin JWT until expiry; possession of a stolen refresh token survives a password reset. Repeated rotation can extend access beyond the original token's lifetime.

Fix: check active/verified status on refresh; introduce server-side sessions or a token/session version checked on protected requests. Revoke sessions on password reset, deactivation, and sensitive role changes. Require access-token type and issuer in the API filter. Keep short access lifetimes as an additional control.

Verification: obtain tokens, deactivate or demote the user, then retry protected endpoints and refresh. Repeat after password reset. An existing SSE connection should also stop receiving private events after revocation.

**F03 — High: concurrent cancellations can restore stock twice; concurrent status changes can overwrite each other.**

Evidence: [OrderService.java](../../backend/src/main/java/com/uitmerch/backend/order/service/OrderService.java), `cancelCustomerOrder` at line 466, `cancelOrgOrder` at line 501, status updates at line 330, and pickup scheduling at line 392. All use ordinary `findById` followed by state validation and save. [Order.java](../../backend/src/main/java/com/uitmerch/backend/order/entity/Order.java) has no version column; [OrderRepository.java](../../backend/src/main/java/com/uitmerch/backend/order/repository/OrderRepository.java) has no locking read. `saveAndFlush` fixes persistence-context clearing, but does not make the preceding state check atomic.

Interleaving: two transactions read PENDING; both set CANCELLED; each restores the same quantity. Confirmation racing cancellation can similarly leave a confirmed order with restored inventory. Two checkout requests can also both create orders when stock is sufficient because checkout has no idempotency key or exclusive cart processing.

Fix: atomically claim an allowed transition using a conditional update, or lock the order while validating and changing state. Restore stock only for the winning cancellation. Apply the same discipline to schedules and check-in. Add idempotency to checkout and instant/guest order creation.

Verification: synchronized parallel cancellation requests for one order must produce one successful transition and exactly one restoration. Race confirmation against cancellation and schedule assignment against cancellation. Retry checkout with one idempotency key and assert one resulting order set.

**F04 — High: merchandise edits can overwrite concurrent stock deductions.**

Evidence: [MerchService.java](../../backend/src/main/java/com/uitmerch/backend/merch/service/MerchService.java), `updateMerch` at line 99; [MerchItem.java](../../backend/src/main/java/com/uitmerch/backend/merch/entity/MerchItem.java), line 23; [MerchItemRepository.java](../../backend/src/main/java/com/uitmerch/backend/merch/repository/MerchItemRepository.java), `deductStock` at line 50. Ordinary entity updates coexist with bulk stock updates. There is no optimistic version or shared locking convention. Default Hibernate entity updates can write a stale stock value even when the organizer only changes the name or description.

Interleaving: an organizer reads stock 10; checkout deducts to 9; the organizer saves the previously loaded entity and can put stock back to 10. An explicit stale stock edit has the same inventory-loss problem.

Fix: use a consistent inventory mutation boundary, such as atomic stock adjustments and conditional updates or shared row locking. If adding optimistic versions, bulk deduction/restoration must participate in version changes too; adding `@Version` only to the entity is insufficient.

Verification: pause an organizer edit after loading the entity, complete checkout, then finish the edit. The final inventory must still reflect the purchase. Repeat with a stock adjustment.

**F05 — High: logged-in product-page preorders become guest orders.**

Evidence: [ProductDetailPage.tsx](../../frontend/src/pages/ProductDetailPage.tsx), line 267 calls `createGuestCheckoutOrder` unconditionally. The visible preorder button at line 384 opens that form for all users. The authenticated `handleBuyNow` at line 215 exists but has no call site. [OrderService.java](../../backend/src/main/java/com/uitmerch/backend/order/service/OrderService.java), line 236 explicitly sets `userId(null)` for guest orders.

Impact: a customer can place an order while logged in and then find no entry in their account history, no customer cancellation action, and no in-app order notifications. Passing the Authorization header to the public endpoint does not attach the account. The UI also discards the response containing the order IDs.

Fix: route customer submissions through the authenticated order flow and preserve recipient details in that flow. Reserve guest checkout for the guest path. Display the actual returned order IDs/tracking action after checkout.

Verification: place a product-page preorder as a customer, then open order history and cancel it. Repeat as a guest and verify the tracking receipt works.

**F06 — High availability risk: public visual search has no application quota or upstream timeout.**

Evidence: [AiMerchSearchController.java](../../backend/src/main/java/com/uitmerch/backend/ai/controller/AiMerchSearchController.java), line 26 is public and lacks the rate limiter used by guest checkout. [GeminiVisionAiService.java](../../backend/src/main/java/com/uitmerch/backend/ai/service/GeminiVisionAiService.java), lines 31 and 73, and [GeminiEmbeddingService.java](../../backend/src/main/java/com/uitmerch/backend/ai/service/GeminiEmbeddingService.java), lines 32 and 69, create HTTP clients/requests without connection or request timeouts and make blocking calls.

Impact: repeated uploads can consume provider quota and request threads; stalled provider calls can occupy threads indefinitely. Actual deployment-level protection and exploitable throughput were not measured.

Fix: add per-client and global quotas, bounded concurrent calls, connection/request timeouts, bounded retries with backoff, and a circuit breaker. Reuse a cached result for identical images where appropriate. Return a temporary-unavailability response without disclosing provider details.

Verification: simulate a provider that never responds and send parallel searches. Requests must terminate within a defined budget, and excess traffic must be rejected without additional provider calls.

**Deployment-dependent security checks**

These are unresolved exposures, not confirmed live vulnerabilities:

| Condition to check | Local evidence | Required decision/check |

| Known demo accounts on a public database | V12 and V14 create verified organizer/admin accounts with a documented shared password; normal Flyway locations include these migrations | Verify whether those accounts remain enabled on the public demo. | Supabase upload authorization | [supabaseClient.ts](../../frontend/src/api/supabaseClient.ts):10 creates an anon-key client; [storage.ts](../../frontend/src/api/storage.ts):39 uploads directly. | Multiple backend instances | [TokenBlacklistService.java](../../backend/src/main/java/com/uitmerch/backend/common/service/TokenBlacklistService.java):36 loads the blacklist at startup; requests consult only the local map. | Image acceptance | Browser upload checks trust File.type and accept SVG; backend storage checks MultipartFile Content-Type and accepts SVG too | Verify bucket MIME/size policies and authorization. Further session-hardening check: JWT generation has no unique token/session identifier. Repeated issuance for the same user with identical second-resolution claims can produce the same token; immediate refresh could blacklist a token and then return that identical token. Reproduce same-second issuance and ensure each rotated refresh credential is unique and consumed atomically. No runtime reproduction was possible here.

Public guest checkout also reserves inventory immediately without email proof or an automatic expiry flow found in the reviewed code. One valid request can reserve a large available quantity. Decide an explicit reservation duration and abuse-control policy; release expired reservations once, through the same concurrency-safe inventory boundary.

**Suggested implementation order**

1. Repair OTP accounting and session revocation; fix customer preorder routing and nested request validation.
2. Make order transitions, stock adjustments, and checkout retries safe under concurrency; add PostgreSQL integration coverage for those guarantees.
3. Bound AI calls; correct publication filters, Swagger settings, mail escaping/delivery, and cache invalidation. Resolve actual Supabase policies and demo-account exposure.
4. Review dependency upgrades and split route/3D code; establish baseline browser performance and end-to-end checkout checks.
5. Add restock/club alerts, then a QR pickup pass. Evaluate campaigns and recommendation refinements using the proposed measures.

Any application-symbol changes should follow AGENTS.md: run upstream GitNexus impact analysis and report callers/processes/risk before editing, warn on HIGH/CRITICAL impact, and run detect-changes before a commit.
